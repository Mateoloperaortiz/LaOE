## Local

- OrbStack como runtime de contenedores: `docker compose up -d` levanta Postgres 18 en `127.0.0.1:5433` (el 5432 lo usa GHPOINTS) y Garage como bucket S3 en `127.0.0.1:3900`; `npm run storage:init` aplica el CORS del bucket con el mismo comando que se usa contra Railway. Mailer de consola.
- `npm run db:reset`: esquema desde cero con las migraciones SQL de Drizzle, verificación de los índices únicos y GIN que declara el esquema (ADR-079) y de las extensiones, y datos sintéticos sin información real.
- `npm test`: solo unitarias. `npm run check` añade Biome, sintaxis Bash, tipos, dependency-cruiser, knip, el extractor Python, integración y `next build`. No incluye E2E ni la restauración de respaldos. `npm test` y `npm run test:integration` pasan el informe de Vitest por la misma comprobación de la compuerta del CI (`verifyVitestReport`, [ADR-120](adr/ADR-120-reglas-de-correccion-del-octavo-ciclo.md) regla 14): un caso saltado, `todo` o dejado afuera por un `only` hace fallar el comando con «Vitest omitió casos». Filtrar por archivo pasa; para filtrar por nombre se usa `npx vitest run --project unit -t "…"`, que no comprueba el informe.
- `npm run test:extractor`: once pruebas Python del extractor con PDFs sintéticos, también incluidas en `check`.
- `npm run test:integration`: PostgreSQL local en una base con sufijo `_test` (la crea y migra `tests/integration/global-setup.ts`). El helper rechaza destinos remotos, protocolos distintos de PostgreSQL y nombres de base ausentes. El setup fija correo de consola, jobs deshabilitados y OTP sintético, independientemente del `.env` de desarrollo. Necesita el superusuario del PostgreSQL local de pruebas: `tests/integration/e2e-baseline.test.ts` prueba la restauración de la E2E con `session_replication_role` ([ADR-116](adr/ADR-116-reglas-de-correccion-privacidad-y-permisos.md) regla 21). Entre pruebas la base se vacía borrando y pasando `VACUUM`, no truncando (ADR-119 regla 23): truncar le dejaba a PostgreSQL cerca de un millón de archivos por corrida y frenaba la E2E que corriera a continuación.
- `npm run test:e2e`: Playwright (Chromium), con comprobaciones de `axe`, un worker y cero reintentos por defecto. Sin filtro corre contra el build, que es lo que prueba el CI: el lanzador compila con `npm run build` y el entorno de la corrida (su mismo `APP_URL`, `NODE_ENV=production` y sin el OTP fijo, como el paso «Build de producción para e2e») y levanta `next start`. Con un filtro de archivos o de nombre (`E2E_FILES`, un archivo, `--grep` o `-g`) corre contra `next dev` sin compilar nada: dev compila cada ruta la primera vez que se visita y sirve para iterar sobre unas pocas. `E2E_SERVER=build` o `E2E_SERVER=dev` fuerza cualquiera de los dos, y con `CI=true` va contra el build que ya esté, sin compilarlo. La corrida completa no va contra dev porque sin nada compilado, como en un worktree nuevo, se atasca hacia su minuto 8 y lo que cae ahí se queda sin tiempo (DT-338). La E2E que cierra un tramo es `npm run test:e2e` sin más. El build queda en `.next` y lo de dev en `.next/dev`: ninguno pisa al otro ([ADR-123](adr/ADR-123-reglas-de-verificacion-y-correccion-del-undecimo-ciclo.md) regla 1). El launcher crea, migra y siembra una base local desechable y la elimina al terminar; solo toma de `DATABASE_URL` la conexión y las credenciales. Necesita el superusuario del PostgreSQL local de pruebas. El setup prepara dos sesiones con contraseña y guarda la base autenticada; cada caso restaura esa copia antes de preparar sus propios datos. La restauración borra las filas y las vuelve a insertar, sin truncar las tablas, y deja cada secuencia donde iba al guardar la copia ([ADR-116](adr/ADR-116-reglas-de-correccion-privacidad-y-permisos.md) regla 21), y la fixture anota lo que tardó cada una en `test-results/restore-baseline.jsonl`. El OTP es sintético. El drenaje final y los anteriores a las limpiezas exigen cero errores del outbox, incluidos los reintentos aplazados.
- `npm run test:backup`: harness Docker aislado que comprueba cifrado, retención, fallos y restauración real de PostgreSQL y medios. Es un job separado de CI y debe ejecutarse además de `check` y E2E para cubrir las cinco familias.
- `npm run dev` y revisión en navegador a 360, 768 y 1280 px, claro y oscuro, navegación por teclado, `axe` sin violaciones serias o críticas, Lighthouse con PWA instalable.

Si el puerto 3000 está ocupado, la suite admite `E2E_PORT`. El build y el servidor de prueba deben usar el mismo origen, y el lanzador lo cumple solo: compila con el `APP_URL` del puerto de la corrida. Quien reutilice con `CI=true` un build ya hecho tiene que haberlo compilado con ese origen: `APP_URL=http://localhost:3105 npm run build` seguido de `E2E_PORT=3105 CI=true npm run test:e2e -- --retries=0`. Las subidas directas al bucket no piden preparar nada: el lanzador suma `http://localhost:<E2E_PORT>` al CORS del bucket local antes de correr, sin quitar los orígenes de otras sesiones ni reescribir uno que ya esté ([ADR-077](adr/ADR-077-el-lanzador-e2e-suma-su-origen-al-cors-del-bucket.md)); Garage usa una regla CORS por origen. `npm run storage:init`, en cambio, reemplaza la lista entera por la de `APP_URL` más `MEDIA_CORS_ORIGINS`: corrido en local mientras otra sesión tiene la suite en otro puerto, le quita su origen hasta que esa sesión vuelva a lanzar. La suite siempre arranca su propio servidor y rechaza bases y buckets que no sean locales.

Para comprobar independencia del orden: `E2E_ORDER=reverse npm run test:e2e` ejecuta los archivos en orden inverso, cada uno con su preparación por caso. Para aislar un recorrido se usa `npm run test:e2e -- tests/e2e/normativa.spec.ts --grep "busca un artículo"`. No hace falta sembrar la base a mano antes de ninguno de estos comandos. `--list` solo enumera y no crea una base.

`tests/e2e/calendar.ts` calcula el término sintético actual y el anterior en Bogotá; `calendar-seed.ts` adapta los IDs del seed en la base desechable. Las pruebas de calendario incluyen 2027, cambio de semestre y 2028 bisiesto. Las de integración invocan la resolución real de `getCurrentTerm()` con el reloj de Vitest; el navegador de la suite completa conserva el reloj real. Los ejemplos históricos de reglas y documentos no son fechas vigentes de la OE.

## CI y verificación de deployments (ADR-053, ADR-054 y ADR-055)

GitHub Actions clasifica el rango completo del cambio. Calidad, respaldo, dos particiones de integración y cinco particiones E2E se ejecutan en máquinas independientes. Cada partición es una lista de archivos calculada por `node scripts/ci/run.mjs e2e-shard k/5` o `integration-shard k/2` desde las duraciones versionadas en `scripts/ci/e2e-durations.json` y `scripts/ci/integration-durations.json` (ADR-054 y ADR-055). Para reproducir una partición E2E sobre el build local: `E2E_FILES="$(node scripts/ci/run.mjs e2e-shard 1/5 | sed -n 's/^files=//p')" CI=true npm run test:e2e -- --workers=1 --forbid-only`; repetir hasta `5/5`. Con `CI=true` usa el build que ya esté; sin él, `E2E_FILES` es un filtro y la partición iría contra dev. Para una de integración: `npm run test:integration -- $(node scripts/ci/run.mjs integration-shard 1/2 | sed -n 's/^files=//p')`. Cada máquina ejecuta un solo caso a la vez y la autenticación E2E se repite en cada una.

El check final `CI` contrasta el inventario completo con los cinco informes E2E y con los dos de integración, y exige que cada uno contenga exactamente los archivos de su partición, la anotación del drenaje estricto en cada escenario, autenticación completa por partición, cero saltos/reintentos y todos los jobs requeridos aprobados. Guarda `ci-result.json` y los tiempos individuales durante 14 días. En una promoción con evidencia reutilizable, el check verifica el `ci-result` de `main` del mismo SHA y lo registra como `reused`. Las unitarias de `ci-policy`, `ci-reports`, `ci-partition`, `ci-promotion` y `ci-smoke` prueban rechazos de omisiones, cancelaciones, referencias desconocidas, repartos incompletos, evidencia incoherente y metadata de deployment incoherente.

Los cambios limitados a la lista de `scripts/ci/documentation-paths.json` validan el diff y emiten el mismo check final, con los jobs pesados omitidos explícitamente. Todo cambio desconocido y toda ejecución manual de CI ejecutan la suite completa. Web utiliza la misma lista para sus exclusiones de autodeploy; copy no está excluido.

`Smoke de Railway` se ejecuta después de un deployment exitoso, con el SHA y las expectativas del entorno verificado, mediante `npm run smoke`. Puede lanzarse manualmente con un ID de deployment de GitHub. Su resultado no se usa como requisito anterior al mismo deployment; las seis comprobaciones HTTP y el artefacto quedan registrados por separado.

## Carnet en billeteras (fase 8, ADR-040)

La suite automática no usa secretos reales ni entrega datos a Google. Integración inyecta certificados/clave RSA de juguete y transporte Google; E2E levanta su propio servidor con Apple de juguete y Google apagado, sin reutilizar un `next dev` con credenciales. En CI y en la corrida completa local se prueba `next start` sobre el build. Un 404 inesperado de Apple hace fallar la prueba; no se oculta con `test.skip`. La habilitación real de un proveedor es otra comprobación y queda pendiente sin sus cuentas.

### Pruebas automáticas

- **Configuración:** ninguna plataforma, solo Apple, solo Google y ambas; los grupos parciales fallan, valores vacíos equivalen a ausentes. Un sufijo Google sin credenciales es válido y mantiene el proveedor apagado. Sufijos e identificadores válidos, claves privadas confinadas al servidor e IaC que preserva las variables opcionales por entorno.
- **Token y membresía:** creación única concurrente, QR opaco válido, rotación auditada, revisión creciente, `readCarnet` compatible con `oe1`, `REVOKED` para tokens viejos y `MALFORMED` para basura; rechazo por generación anterior aunque haya baja/reactivación antes de drenar. Anonimizar invalida localmente en la misma transacción. Resolver actualiza uso solo cuando el token corresponde al estado vigente.
- **Apple:** JSON y campos accesibles sin correo/foto/puntos, sin término/comités, nombres largos, imágenes en sus escalas, serial estable. Descomprimir ZIP, comparar manifiesto con hashes de todos los archivos y verificar criptográficamente la firma CMS con CA/certificado de juguete. La ruta responde MIME, nombre de archivo y `no-store`; una firma fallida no estampa emisión. Verificar carga de imágenes/certificado desde el build, no solo desde TypeScript.
- **Google:** firma RS256 comprobada con la clave pública, claims de guardado con `id` y `classId`, OAuth2 y timeout. Primera emisión reserva local antes de REST; un POST exitoso seguido de fallo local/reintento converge al mismo objeto. Emisiones concurrentes resuelven 409 sin duplicar; posteriores actualizan. Un 404 de sincronización marca revocado y no crea de nuevo; reemisión propia explícita sí puede recuperar. Ningún job crea el primer token/pase.
- **Jobs y concurrencia:** cambio de nombre/comité, rotaciones repetidas antes de drenar, eventos duplicados, fallos transitorios, carrera emisión/revocación/baja y baja/reactivación/anonimización. El lock de red no retrasa revocación. Un resultado viejo no adelanta snapshots vigentes. Eventos de campos no visibles no llaman a Google. Sin variables las limpiezas permanecen pendientes y la fila no se pierde; con variables restauradas terminan.
- **Semestre:** reloj de Bogotá antes/después de medianoche, roster cargado para término futuro, inicio sin nuevo evento y ausencia de término. El tick de las 00:05 pagina más de 100 pases y concilia todos sin publicar anticipadamente el futuro. Comprobar que vuelve a enviar por PUT los pases vigentes aunque coincidan generación, revisión y término: debe recuperar cambios de nombre/comités cuyo evento no llegó a procesarse. El aviso Apple usa generación/revisión/término de su snapshot, no una comparación de timestamps.
- **Supresión y exportación:** baja produce `EXPIRED`; anonimización reemplaza todo el objeto por mínimos sin nombre personal, QR, módulos ni enlaces anteriores. Solo éxito/404 permite borrar la referencia local. Mis datos incluye estados/fechas, sin tokens ni credenciales, JWT o contenido privado del pase.
- **E2E y acceso:** miembro descarga Apple, `oe1` permanece en pantalla, revoca desde Mi OE y ADMIN desde 360; actor sin permiso no revoca otra persona. La 360 distingue reserva pendiente, emitido y revocado. Gestión/avisos siguen visibles con proveedores retirados; sin registros y sin proveedores no hay emisión. Sin sesión redirige al ingreso; proveedor apagado responde 404; errores devuelven el texto inventariado. Google nunca se llama desde E2E.

### Credenciales de juguete y firma

`tests/fixtures/wallet/toy-credentials.json` contiene claves deliberadamente públicas y desechables. Base64 facilita la carga; no es protección ni garantiza que un detector de secretos las ignore. La CA de juguete firma el certificado de pruebas y su clave privada no se versiona. Receta ejecutada en un directorio temporal:

```sh
openssl req -x509 -newkey rsa:2048 -nodes -days 36500 -subj '/CN=OE Test CA/OU=TEST ONLY' -keyout wwdr.key -out wwdr.crt
openssl req -new -newkey rsa:2048 -nodes -subj '/CN=Pass Type ID: pass.test.oe/OU=TESTTEAM00/O=OE Test' -keyout signer.key -out signer.csr
openssl x509 -req -in signer.csr -CA wwdr.crt -CAkey wwdr.key -set_serial 1 -days 36500 -out signer.crt
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out google.key
openssl pkey -in google.key -pubout -out google.pub
```

Se codifica el PEM con `Buffer.from(pem).toString("base64")`: `wwdr.crt` → `wwdr`, `signer.crt` → `signerCert`, `signer.key` → `signerKey`, `google.key` → `googleKey`, `google.pub` → `googlePublicKey`. Para comprobar la cadena, la prueba pasa el certificado/CA toy mediante el override de certificados de `signPass`; el runtime normal usa el WWDR G4 público versionado y no un override de pruebas. E2E usa la clave/certificado toy para ensayar la descarga: no supone que esa cadena sea confiable para Apple.

La prueba extrae las entradas del pase, recalcula sus SHA-1 y compara con `manifest.json`. La firma CMS y la cadena de juguete se verifican, sin `-noverify`, con:

```sh
openssl cms -verify -inform DER -binary -in signature -content manifest.json -CAfile wwdr.crt -purpose any
```

La receta y la huella del [WWDR G4 público](https://www.apple.com/certificateauthority/AppleWWDRCAG4.cer) están en `tests/fixtures/wallet/README.md`. Su clave privada no forma parte del proyecto. El certificado de firma real y su clave solo se suministran mediante variables privadas del entorno.

### Biblioteca de juegos y 2048 (ADR-075)

`tests/unit/game2048-engine.test.ts` es el corazón de la garantía: determinismo de la misma semilla en partidas completas, divergencia entre semillas, ausencia de coma flotante, las reglas de fusión (`2 2 4 4 → L` da `4 8 0 0` sumando 12; `4 4 4 4 → L` da `8 8 0 0`, no `16`), el movimiento inerte que devuelve `null`, el reparto de fichas de 4 alrededor del 10 %, y el replay que rechaza la lista entera si trae un movimiento inerte, un carácter ajeno, una semilla mal formada o más movimientos que el tope. Comprueba además que un puntaje inventado no se reproduce y que cada umbral de premio queda por debajo del costo de fusiones de su ficha.

`tests/integration/game2048.test.ts` cubre el comando: leer no crea partidas, la semilla sale a su dueño con la partida abierta y nunca al historial ni a la auditoría, repetir el inicio devuelve la misma partida (veinte inicios concurrentes dejan una sola), el cierre acredita el puntaje del servidor con su entrada de ledger y su evento, reenviar el mismo `requestId` no acredita dos veces y con otro contenido se rechaza, dos cierres concurrentes de la misma partida dejan un solo premio, la segunda partida del día se guarda sin acreditar aunque también pase el umbral, la base rechaza un segundo crédito forzado por su índice parcial y no por otra regla, una partida bajo el primer umbral no consume el crédito del día, la medianoche y el cierre de puntos vencen la partida sin acreditar, quien no es activo ni honorario no juega y una partida ajena responde como inexistente. Las siete pruebas que necesitan un crédito juegan con una semilla fija que la heurística de la prueba lleva sobre el primer umbral, y lo comprueban al abrir la partida: con la semilla aleatoria del servidor esa heurística se queda bajo 1.000 puntos en el 2,5 % de las partidas, y el archivo fallaba por azar en una de cada seis corridas.

`tests/e2e/juegos.spec.ts` juega **de verdad**: elige cada dirección con el mismo motor, bien (más casillas libres) hasta pasar el primer umbral o a cerrar el tablero cuanto antes (sin parejas que juntar y lleno). La semilla la reparte el servidor y ninguna manera de jugar asegura el resultado: en 100.000 semillas, jugar bien se quedó bajo el primer umbral en el 2,4 % y jugar a cerrar no lo pasó en ninguna. Por eso la prueba no supone el premio (DT-095): al cerrar cada partida lee el puntaje de la pantalla y exige lo que le toca a ese puntaje, que es el texto del premio con sus puntos, el de «todavía no sumás» o el de «hoy ya sumaste», y en la base el puntaje guardado, los puntos acreditados de esa partida y la única entrada del ledger; cada corrida deja anotado qué caso vio. Comprueba la biblioteca desde el resumen de GH Points, un día de tres partidas reales con recarga entre una y otra (una a cerrar y dos bien jugadas: la que llega con el crédito del día tomado se guarda sin sumar), retomar tras recargar con el tablero y el puntaje exactos después de doce jugadas comprobadas, y el móvil a 390 px con los cuatro botones de dirección, sin desborde horizontal y con axe WCAG A/AA en claro y oscuro. Toda prueba que empieza una partida espera los controles de dirección antes de leer el tablero (`empezarPartida`): la partida nace en una transición y, leído antes, el tablero son dieciséis ceros. La mudanza del tablero del Wordle se comprueba en `wordle.spec.ts`, que ahora navega a `/app/juegos/wordle` e intercepta esa ruta para el replay por `requestId`. En el cierre del ciclo 7 la spec corrió veinte veces seguidas (`E2E_FILES=juegos.spec.ts npm run test:e2e -- --repeat-each=20`): pasaron las veinte, entre 3,2 y 3,9 s cada una.

Comandos: `npm run check` y `npm run test:e2e -- juegos wordle gh-points mi-oe member-experience pwa gamificacion ledger cierre`.

Revisión visual: biblioteca a 1280 px y tablero a 390 px en claro y oscuro; la barra inferior de Mi OE con sus seis pestañas (medida: 61 px cada una a 390 px, sin desborde ni etiquetas cortadas).

`scripts/ci/e2e-durations.json` **no** se edita a mano: lleva la huella de la corrida de CI que lo generó y el repartidor le da peso mediano a un archivo que no conoce, así que `juegos.spec.ts` se equilibra solo hasta la próxima regeneración.

### Sudoku (ADR-078)

`tests/unit/sudoku-generator.test.ts` sostiene las reglas 4 a 6. Tres semillas fijas reproducen su **tablero literal** —dadas, solución y número de intentos—: si alguien cambia un sorteo, el orden del cavado o una técnica del solver, la prueba falla, y lo que se corrige no es el literal sino `SUDOKU_RULES_VERSION`. Sobre 120 semillas por dificultad que salen de un contador comprueba que la solución es una cuadrícula válida de la que salen las dadas, que hay **exactamente una solución** contada con un backtracking aparte del solver lógico, que el tablero exige la técnica de su dificultad y **se traba con las del nivel anterior**, y que respeta el piso de dadas y la simetría de 180°. No hay aserciones de tiempo: los números viven en la ADR y salen de `node --import tsx scripts/sudoku-bench.ts 20000 1000`. `tests/unit/sudoku-engine.test.ts` cubre la geometría, los formatos, los repetidos y la tabla de premios contra los checks de la base, y `tests/unit/sudoku-play.test.ts` el reductor del estado de juego: dígitos, notas que se limpian en fila, columna y caja, pistas que dejan la casilla fija, errores contra la solución y la partida guardada en el navegador, que se descarta si no tiene forma de partida o no conserva las dadas.

`tests/integration/sudoku.test.ts` cubre el comando sin azar: la prueba lee la solución de la fila, que es lo único que la conoce, así que ningún crédito depende de la suerte ni de un solver propio. Comprueba que leer no crea partidas y que el tablero repartido es coherente con lo guardado; que **sin ayudas la solución no aparece en ninguna respuesta** —inicio, inicio repetido, lectura del día, cierre fallido, cierre e historial— y con ayudas viaja solo con la partida abierta; que la semilla no aparece nunca, ni en la auditoría ni en los eventos; los seis premios de la tabla con su entrada de ledger, su motivo y su evento; que una cuadrícula equivocada, o la solución de otro tablero, deja la partida abierta **sin escribir auditoría**; veinte inicios concurrentes que dejan una partida; el rechazo de otra dificultad u otro modo con una abierta; abandonar, que es idempotente y libera el día; el `requestId` de inicio de una partida cerrada, que responde terminada y no un error; el reenvío del cierre, el mismo `requestId` en otra partida y seis cierres concurrentes con un solo premio; «un Fácil con ayudas primero y el Difícil después da 0»; el segundo crédito forzado que la base rechaza por su índice parcial; el check que impide acreditar más de 3 con ayudas; la medianoche, el día siguiente, el cierre de puntos, la elegibilidad, la partida ajena y una sola interacción de CRM sin push. `tests/integration/gamification-own-data.test.ts` comprueba que `Mis datos` exporta las partidas sin semilla, dadas ni solución.

`tests/e2e/sudoku.spec.ts` juega con la solución que lee de la base, como ya hace `juegos.spec.ts` con las partidas del 2048. Resuelve un Difícil sin ayudas con el teclado físico y comprueba que acredita 6 y que **ni la página ni las respuestas de las acciones trajeron la solución ni la semilla**, y que el segundo tablero del día se guarda sin sumar. Los cuerpos de las acciones se leen desde Node con `page.route` y `route.fetch`, solo para los POST: `response.text()` depende del búfer del navegador y en el runner de CI devolvió vacío, y retener también el documento o los refrescos retrasa la hidratación y confunde al cliente de Next. Lo que el servidor manda para pintar la página se lee del DOM tras recargar a mitad de partida, donde quedan los datos que Next incrusta para hidratar. La comprobación exige además que las dadas **sí** hayan viajado y que ningún cuerpo llegue vacío, para no pasar en vacío: esa exigencia fue la que destapó el problema en CI. Las pruebas entran por `abrir`, que espera a que React tome el formulario: los radios son controlados y un clic anterior a la hidratación se pierde; con ayudas marca un error al instante, lo borra, pide una pista que deja la casilla fija y acredita 1; recargar conserva dígitos y notas, deshacer quita la última, las flechas mueven el foco y la selección juntos, y abandonar deja elegir otra dificultad; y en un móvil de 390 px se juega solo con el teclado en pantalla, con casillas de 34 px o más, sin desborde horizontal y con axe WCAG A/AA en claro y oscuro con un repetido, un error, una nota y una pista a la vista. Toda prueba que empieza un tablero espera la grilla antes de leer la base.

Comandos: `npm run check` y `E2E_FILES=sudoku.spec.ts,juegos.spec.ts npm run test:e2e`. **Ojo con el filtro posicional de Playwright**: compara contra la ruta completa, así que `npm run test:e2e -- sudoku` dentro de un worktree que se llame `sudoku` corre la suite entera; `E2E_FILES` no tiene ese problema.

Revisión visual: pantalla de inicio y tablero a 1280 px, y tablero a 390 px en claro y oscuro, con los cuatro controles del teclado (icono arriba y texto abajo, que es como caben cuatro a 390 px) y la biblioteca con sus tres tarjetas en una fila.
